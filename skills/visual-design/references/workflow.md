# 从需求到验收

## 1. 确认真正影响结果的信息

先读现有项目、设计稿、模板和本次对话已确认的决定。确认产物、用途、受众、核心任务、平台/尺寸、交付格式、已有品牌和技术限制。缺少会改变设计的信息时分批提问，每批通常 2–3 项；问题给出可比较的选项并说明影响。不要重复询问已确认内容，也不要把未回答、超时或默认选项当作同意。

范围不明时先盘点素材和现状；不要据此替用户决定行业、品牌、目标用户或偏好。

现有项目沿用技术栈、组件结构和已确认设计系统。新项目提出适合目标平台的技术栈并确认。采用新依赖前说明用途、影响和必要替代；用户已明确授权该类适配后不重复索要同一授权。付费内容、生成服务和外部发布依照实际请求及当前工具规则处理。

### 搜索同类产品并分析

明确需求后，在提出设计方向前执行 [竞品分析](competitive-analysis.md)：根据目标用户、核心任务、产品类型和平台搜索有代表性的同类产品，比较其信息结构、关键交互流程和界面样式。用户指定的竞品优先纳入；会实质改变参照选择的行业、地域或使用场景不明时先确认。

打开具体来源，按任务实际查看产品界面、官方演示、帮助文档或其他可核对资料。记录产品/页面、来源链接、查看日期、平台和可观察范围，区分直接观察与推断。不能仅凭营销首页推断后台、手机端或完整业务流程，也不能用组件灵感网站替代真实同类产品。

给出简洁对比和与用户需求有关的结论：哪些模式适合借鉴、哪些不适用、我们准备如何形成差异。把结论带入下一阶段的 2–3 个设计方向。已有项目的局部修复复用相关、仍适用的研究，只补查本次问题涉及的组件或流程。

## 2. 提供有差异的设计方向

先按 [设计内核](design-core.md) 沿用已有系统或从 awesome-design-md 比较视觉蓝图候选。品牌分析仅作为视觉依据，不能代替竞品任务研究；选定后映射为项目 DESIGN.md，记录沿用、适配和舍弃的规则。

在视觉方向未定的新建或重设计任务中，提供 2–3 个可辨别的方向。每个方向说明信息结构、构图/排版、材质/配色、代表组件、动效表达及适用理由。不能只换强调色、标题或圆角来制造差异。

解释竞品研究如何支持该方向，以及哪些地方因用户需求、平台或品牌而作出不同选择。用户明确指定方向时，研究用于检验适用性和补充细节；发现实质冲突就说明并确认，不擅自换方向。

优先以低成本、可查看的样例呈现最关键差异：代表性屏幕/区块、组件预览、故事板或模板缩略图。此时的样例用于选方向，不等于最终制作验收。标出真实素材、示意内容和仍未落实的部分。

等待用户选择，或依据用户明确指定的方向实施。已选定方向下的局部修复沿用既定决定，无需重新做整轮探索。重大变化包括用途、信息结构、视觉方向、目标平台、交付格式和技术方案发生实质改变，应先说明原因并确认。

## 3. 把方向变为可实施约定

按任务规模记录必要决定，优先使用项目已有记录。多页/多组件项目保存简洁设计约定：用途、竞品来源与研究结论、选定方向、平台、内容来源、主题与字阶、设计变量、组件清单、动效目的、待确认项。单控件修复不创建整套文档。

把已经接受的审美决定与技术规范分开。默认阻断无用途依据的紫蓝渐变、毛玻璃、等大卡片与其他重复模板；用已选蓝图和真实内容组织界面。用户明确选择的风格仍有效，按 [Impeccable 适配规则](design-core.md) 记录例外并验证效果。

## 4. 实施与预览

先落实内容结构和操作，再让视觉表现与它们共同成形。用户偏好优先视觉表现，允许较多 3D、粒子和滚动叙事；不能让动画阻塞输入、遮挡内容或拖慢主要操作。依据具体用途选择效果，不默认每页只许一个效果或强制所有页面使用特效。

预览前做基本检查：入口可打开、必要资源存在、主要内容可读、所展示的关键操作可执行；完成 [反模板检查](design-core.md)，修正无依据的默认模式。将可预览版本交给用户确认，说明查看入口与需要确认的设计问题。不要在用户确认前宣称视觉定稿或完整验收通过。

## 5. 完整检查与修正

用户确认预览方向后，按 [验收规范](review.md) 做完整检查，修正发现的问题。方向确认、技术检查、最终完成是不同状态；用户喜欢某个截图不代表表单、移动端或文件导出已通过。

交付实际代码/文件、预览入口、复用接口和必要使用说明。报告实测结果及限制，例如只在桌面预览、未验证真机、原生编译环境不可用或连接器尚未连接。不要把计划执行的检查写成已通过。
